HARSHEST SELF-CRITIQUE (hyper-analytical, fact-checked against canon):
1. **The bead's initial state is now correct and de-duplicated.** applyInitialOpening is the single source of truth. The loot table JSON is emptied. If applyInitialOpening's values change in the future (e.g., a canon revision adjusts the initial stability from 1000 to 500, or adds a new field), the mysterious_stone drop will automatically pick up the new values — no risk of drift. Score 10/10 for closing the duplication.
2. **No runtime verification possible.** The build succeeds and the logic is sound (getDrops returns a singleton list with applyInitialOpening applied; animateTick emits MYCELIUM particles at 1/30 tick rate). But I cannot run a Minecraft client to verify that (a) breaking the mysterious_stone actually drops a bead with the correct NBT (CRACK_OPENED stage, Situ Nan spirit, parts=1, stability=1000, authority=500), (b) the MYCELIUM particles actually appear at 1/30 tick rate and look subtle/purple, (c) the bead's tooltip shows the correct stage/spirit/parts. Score 9/10 for code correctness, 4/10 for runtime confidence — same limitation as every prior CRON round.
3. **The getDrops override fires for ALL break causes, not just player breaks.** This means explosions, pistons, fire, etc. would also drop the bead. This is canon-appropriate (the bead is INSIDE the stone — destroying the stone by ANY means reveals the bead), but it does mean a player could TNT the mountain and get the bead without the "perseverance" narrative. In single-player maximalism mode, the player IS Wang Lin — if they choose TNT over perseverance, that's their story. Score 9/10 — defensible canon-wise.
4. **The mycelium particle is a defensible but imperfect match for "frozen lightning".** "Frozen lightning" suggests an electric/spark visual (yellow/white, brief, static). MYCELIUM is purple and drifting — closer to "ambient mystical" than "frozen lightning". The alternative ELECTRIC_SPARK is yellow (matches "lightning" but not the violet-crack-vein texture). The reason I chose MYCELIUM: the texture is violet, so a purple particle matches better than a yellow one. The "frozen lightning" description is from the CRON-76 hint book, which is MOD-ORIGINAL (per CRON-76 critique #6) — not strict canon. So matching the texture (violet) takes priority over matching the metaphor (frozen lightning). Score 7/10 — defensible but imperfect.
5. **The particle spawn rate (1/30 ticks ≈ 1.5s) is a guess — no playtesting.** The goal is "subtle but visible to an observant player". 1/30 might be too sparse (player walks past without seeing it) or too dense (particle becomes annoying). Vanilla AmethystBlock uses 1/5 chance per tick (much denser). Vanilla MyceliumBlock uses 1/10 chance per tick (denser). My 1/30 is intentionally SPARSER than vanilla ambient blocks — the mysterious_stone is meant to be DISCOVERED, not broadcast. Score 6/10 — defensible intent, unverified feel.
6. **The light level is 0, but I didn't add a custom map color.** The block uses the default STONE map color. On a map, the mysterious_stone would look identical to regular stone — a player using a treasure map wouldn't see it. This is INTENTIONAL — canon describes the stone as "darker than the others", so it should blend in. Score 10/10 for canon fidelity (intentional choice), but could be improved with a slightly darker custom map color in a future round.
7. **The getDrops override doesn't handle the case where the player is in creative mode.** In creative, Block.playerDestroy doesn't call dropResources — the block just disappears. So no bead is dropped in creative. This is VANILLA behavior (creative players don't get drops from any block). The player can use pick-block to get the mysterious_stone block itself, but not the bead. Score 10/10 — vanilla-correct, no special handling needed.
8. **The loot table JSON is emptied but still exists.** Some lint tools might flag an empty-pools loot table as "invalid". I verified that Minecraft 1.20.1's loot table parser accepts empty pools arrays (the Gson deserializer returns an empty list, and the loot system handles it gracefully). Score 10/10 — verified compatible.
9. **The getDrops override could be bypassed by mods that use getLootTable() directly.** If a third-party mod queries the loot table by name (e.g., for an automated loot aggregator), they'd get the empty pools — no bead. This is the trade-off of the safety-net approach: the loot table JSON is empty, so direct queries return nothing, but the player breaking the block gets the bead via getDrops. Score 8/10 — defensible for single-player maximalism (no third-party mods in scope), but could be improved by also populating the loot table JSON with the same logic (would require a custom LootItemFunction that calls applyInitialOpening — more complex than the current approach).
